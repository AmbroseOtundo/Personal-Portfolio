01. Project Overview

The objective was to build and administer a Linux-based cloud environment on DigitalOcean while gaining practical experience with Linux server administration, database connectivity, container orchestration, remote desktop access and monitoring.

The environment used an Ubuntu 24.04.5 LTS droplet with approximately 2 GB of RAM and a 48 GB filesystem.

Project objectives

  • Provision and administer a Linux cloud server.
  • Configure secure SSH access and troubleshoot authentication.
  • Deploy containerized services using Docker Compose.
  • Implement browser-based remote access using Apache Guacamole.
  • Work with PostgreSQL databases and authentication.
  • Configure infrastructure monitoring using Prometheus and Grafana.
  • Investigate connectivity and service configuration issues.

03. Linux Server Administration

The cloud environment ran Ubuntu Server 24.04.5 LTS. I used the Linux command line for system administration, package management, service troubleshooting and infrastructure configuration.

System information

# Check operating system
cat /etc/os-release

# Check kernel
uname -r

# Check memory
free -h

# Check filesystem usage
df -h

# Check disk information
lsblk

# Check running processes
top

Package management

# Update package repositories
sudo apt update

# Upgrade installed packages
sudo apt upgrade -y

# Install common administration tools
sudo apt install curl wget vim \
  net-tools unzip htop -y

These commands formed part of the Linux administration and troubleshooting workflow.

04. SSH & Remote Access

SSH was used to administer the Ubuntu server remotely. I also investigated public-key authentication problems when connecting to the cloud environment.

SSH connectivity checks

# Check SSH service
sudo systemctl status ssh

# Check listening ports
sudo ss -tulpn

# Review SSH service logs
sudo journalctl -u ssh

# Check SSH configuration
sudo sshd -t

Public-key authentication

I encountered the error: 

Permission denied (publickey)

Troubleshooting involved reviewing SSH keys, client configuration, the authorized_keys file and Linux file permissions. 

# Check SSH directory permissions
ls -ld ~/.ssh

# Check authorized keys permissions
ls -l ~/.ssh/authorized_keys

# Set recommended permissions
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys

Private SSH keys must never be uploaded to a public repository. Only sanitized configuration examples should be included in public documentation.

06. Apache Guacamole & XRDP

I deployed Apache Guacamole using Docker Compose to provide browser-based remote access to a Linux desktop environment. The deployment consisted of three containers.

Container Image Purpose
guacamole guacamole/guacamole:1.5.5 Ib application
guacd guacamole/guacd:1.5.5 Remote desktop proxy
guac-postgres postgres:16-alpine Application database

Container deployment

The Compose environment was maintained in: 

/opt/guacamole/

The main services Ire configured to communicate through the Docker network. Guacamole used the PostgreSQL container for application data, while guacd handled remote desktop connections.

Service verification

# Navigate to deployment directory
cd /opt/guacamole

# Start the Compose stack
docker compose up -d

# Check containers
docker compose ps

# Inspect application logs
docker compose logs guacamole

# Inspect database logs
docker compose logs guac-postgres

# Restart services
docker compose restart

XRDP integration

I also worked with XRDP to provide Linux remote desktop sessions. The XRDP service was configured to use port 8933, with the service bound to localhost. 

# Check XRDP service
sudo systemctl status xrdp

# Inspect XRDP configuration
sudo ss -tulpn | grep 8933

# Inspect service logs
sudo journalctl -u xrdp

Guacamole and XRDP served different roles: Guacamole provided the browser-based access layer, while XRDP provided the Linux remote desktop protocol endpoint.

07. PostgreSQL Database Administration

I worked with PostgreSQL in two contexts: a PostgreSQL container supporting Apache Guacamole and a separate DigitalOcean managed PostgreSQL database.

Managed PostgreSQL connectivity

The Ubuntu droplet was used as a client environment for connecting to the managed database. 

# Install PostgreSQL client
sudo apt install postgresql-client -y

# Connect to a database
psql -h DATABASE_HOST \
  -U DATABASE_USER \
  -d etimsdb -p 25060

The connection parameters above are illustrative. Use the actual connection details supplied by the database provider when configuring your own environment.

Authentication troubleshooting

I encountered a PostgreSQL authentication issue: 

fe_sendauth: no password supplied

I investigated password handling and the PostgreSQL password file, including the use of the .pgpass configuration. 

# Create PostgreSQL password file
touch ~/.pgpass

# Restrict access
chmod 600 ~/.pgpass

# Edit the file
nano ~/.pgpass

The PostgreSQL password file uses this format: 

hostname:port:database:username:password

The credentials and database connection information must remain private.

08. Infrastructure Monitoring

I worked on implementing a monitoring environment using Prometheus, Node Exporter and Grafana, with additional PostgreSQL metrics integration.

Prometheus

Prometheus was configured to collect metrics from monitoring targets using scrape configurations.

Node Exporter

Node Exporter was used to expose Linux system metrics for Prometheus collection.

PostgreSQL metrics

I also added a PostgreSQL metrics endpoint as a Prometheus scrape target, allowing database monitoring to be incorporated into the monitoring environment.

Configuration validation

# Validate Prometheus configuration
promtool check config /etc/prometheus/prometheus.yml

# Check Prometheus service
sudo systemctl status prometheus

# Check Node Exporter service
sudo systemctl status prometheus-node-exporter

# Inspect Prometheus logs
sudo journalctl -u prometheus

I encountered and resolved YAML configuration issues during Prometheus setup. Configuration validation is important before restarting monitoring services.
