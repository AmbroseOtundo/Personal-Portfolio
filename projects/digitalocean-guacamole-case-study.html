1. Executive summary and confirmed state

The solution provides a lightweight Linux desktop in a browser by chaining Apache Guacamole (web client), guacd (RDP
proxy), XRDP (RDP server), and XFCE (desktop environment). PostgreSQL stores Guacamole authentication and connection
data. Docker Compose runs Guacamole, guacd and PostgreSQL; XRDP and XFCE run on the Ubuntu host.
The server was accessed as root over SSH using a key from Windows PowerShell. The final access path is intentionally
private: the Guacamole HTTP service is published only on 127.0.0.1:8080 on the host, and a local SSH tunnel makes that
endpoint available to the browser on the operator PC.

2. Architecture and network flows

Figure 1 shows the intended and observed traffic path. Only the SSH tunnel crosses the public network in the current
configuration. The Docker bridge is used to let guacd reach the host-bound XRDP listener without publishing RDP on a public
interface.

2.1 Connection flow

1.  Windows browser opens http://127.0.0.1:8080/guacamole/.
2.  Windows OpenSSH forwards local TCP 8080 through the SSH session to server-side 127.0.0.1:8080.
3.  Docker publishes only 127.0.0.1:8080 on the host and forwards traffic to the Guacamole container TCP 8080.
4.  Guacamole uses guacd over the Docker network (TCP 4822) and PostgreSQL via the Compose service DNS name
    postgres (TCP 5432).
5.  For the desktop connection, guacd reaches the host gateway 172.28.0.1 on TCP 8933. XRDP creates/reconnects the
    xmldesktop XFCE session.
6.  Host UFW permits TCP 8933 only from the Docker bridge subnet/interface. This is not a public RDP listener.

4. Prerequisites and provisioning the host

4.1 Baseline prerequisites

•  A fresh 64-bit Ubuntu Server 24.04 LTS droplet. The observed instance has 2 GiB RAM and 48 GB disk; for multiple
    concurrent desktop sessions, plan more RAM.
•  SSH key access from the administration workstation. Keep a second SSH session open when changing firewall or SSH
     settings.
•  A DNS name is not required for the current SSH-tunnel approach. A properly secured direct browser portal is a separate,
    not-yet-completed change.
•   Record current firewall policy, addresses and service ports before modifying an existing server.

4.2 Update and install host packages

       apt update
       apt upgrade -y
       apt install -y xfce4 xfce4-session xrdp dbus-x11 acl ufw curl ca-certificates openssl

The installation history confirms XFCE, xfce4-session and XRDP were installed. The other packages above support reliable
XFCE sessions, ACL management and related operations in a repeat build; check package availability for the chosen Ubuntu
point release.

4.3 Install Docker Engine and Compose plugin

The existing server reports Docker 29.1.3 and Docker Compose 2.40.3. For a new Ubuntu host, use Docker’s official Ubuntu
APT repository instructions rather than an unreviewed convenience script. The canonical steps are at reference [1]. After
installation, verify:

       docker --version
       docker compose version
       systemctl is-active docker
       docker run --rm hello-world

  Reproducibility note: Docker package versions and the postgres:16-alpine tag can move over time. For strict rebuild
  equivalence, record package versions and container image digests after a tested deployment; version tags alone are not
 immutable.

The account observed in the current deployment is xmldesktop, UID 1004. Its verified group list included 27(sudo) and
100(users). Do not add xmldesktop to the root group; sudo is the correct Ubuntu mechanism for administrative operations.

5.2 Configure the desktop session

       runuser -u xmldesktop -- sh -c 'printf "%s\n" xfce4-session > /home/xmldesktop/.xsession'
      chown xmldesktop:xmldesktop /home/xmldesktop/.xsession
      chmod 600 /home/xmldesktop/.xsession
        cat /home/xmldesktop/.xsession

Expected .xsession contents: a single line, xfce4-session. If a newly added sudo group does not show up inside an existing
desktop terminal, log out of the Linux session completely and reconnect so the session receives updated group
membership.

5.3 Verify sudo

      sudo whoami

Run that from a refreshed xmldesktop session; enter the Linux password for xmldesktop. Expected output is root. If it still
reports “not in the sudoers file”, verify `id xmldesktop`, log out completely and reconnect. The transcript confirms the group
membership was eventually correct.

6. Docker network, XRDP binding and firewall

6.1 Create the Docker bridge network

     # Inspect first; do not create a duplicate network if desktop-net already exists
       docker network inspect desktop-net

     # For a fresh deployment only, if the network does not exist:
       docker network create --driver bridge --subnet 172.28.0.0/24 --gateway 172.28.0.1 desktop-net

The current network is named desktop-net and uses subnet 172.28.0.0/24 with gateway 172.28.0.1. Docker assigns a bridge-
interface name such as br-<network-id-prefix>; that name is host-specific and must be discovered on each build.

       docker network inspect -f 'Name={{.Name}} Id={{.Id}} {{range .IPAM.Config}}Subnet={{.Subnet}} Gateway={{.Gateway}}{{end}}' desktop-net
        ip -br addr


6.2 Bind XRDP to the Docker gateway

Edit `/etc/xrdp/xrdp.ini`. In the `[Globals]` section, set the port line to the following value. Back up the file before editing.
Do not change unrelated sections.

      cp -a /etc/xrdp/xrdp.ini /etc/xrdp/xrdp.ini.bak.$(date +%F-%H%M%S)
      nano /etc/xrdp/xrdp.ini
     # Under [Globals]:
     # port=tcp://172.28.0.1:8933
       systemctl enable --now xrdp xrdp-sesman
       systemctl restart xrdp xrdp-sesman
       systemctl status xrdp xrdp-sesman --no-pager
        ss -lntp | grep ':8933'

 Expected listener: XRDP should listen on 172.28.0.1:8933, not 0.0.0.0:3389. A listener on a public interface would
  violate the intended design.


6.3 Restrict the firewall rule

Before changing UFW, inspect its rules and ensure SSH is allowed so the administrator is not locked out. The actual bridge
interface in the observed deployment was br-cc92fc8c6a46; this may differ on a new host.

The final observed rule allowed traffic from 172.28.0.0/24 to 172.28.0.1:8933 on the Docker bridge. A broad `ufw allow
8933/tcp` was tried during troubleshooting and then removed; do not recreate that broad rule. Do not run `ufw reset` as a
troubleshooting shortcut.
The captured status also showed incoming default deny, outgoing allow, routed default deny, SSH/TCP 22 allowed, and an
existing TCP 14344 allow rule of unknown purpose. Preserve and investigate existing service-specific rules rather than blindly
replacing the firewall.

7. PostgreSQL and Guacamole deployment

7.1 Create the deployment directory and secret

      mkdir -p /opt/guacamole
      cd /opt/guacamole
      chmod 700 /opt/guacamole

     # Fresh database only: generate a strong URL-safe value for the DB role password
        printf "DB_PASSWORD=%s\n" "$(openssl rand -hex 32)" > .env
      chmod 600 .env

 Secret handling: Never paste `.env` into support chats or store it in source control. Keep a protected record of the
 database password in an approved password manager. If a password is changed after PostgreSQL has initialized its data
 volume, update the database role as well; changing .env alone does not rotate an existing PostgreSQL role password.


7.2 Use the Compose layout

The reference Compose file is reproduced in Appendix A. It reflects the observed names, database and ports. On an existing
deployment, compare it with `/opt/guacamole/compose.yaml` first; do not replace a working file without backing it up. The
Compose file references an external `desktop-net` bridge and a persistent `postgres_data` volume.

7.3 Initialize the PostgreSQL schema once

For a new database only, create the SQL schema using the same Guacamole version as the application and apply it once.
The deployment initially generated this script from version 1.6.0, then the application was downgraded to 1.5.5. For a fresh
rebuild of the currently pinned version, use the 1.5.5 image as shown here:

      cd /opt/guacamole
       docker compose up -d postgres
       docker compose ps

     # Generate schema from the same version as the pinned Guacamole image
       docker run --rm guacamole/guacamole:1.5.5 \
        /opt/guacamole/bin/initdb.sh --postgresql > /opt/guacamole/initdb.sql

     # Apply only to a freshly created, empty guac_db schema
       docker exec -i guac-postgres psql -v ON_ERROR_STOP=1 \
       -U guac_user -d guac_db < /opt/guacamole/initdb.sql

 Never reapply initdb.sql to an already initialized production database. First take a pg_dump backup and check the
  official migration/upgrade procedure for the exact source and target versions.

7.4 Start and validate the stack

      cd /opt/guacamole
       docker compose config -q
       docker compose pull
       docker compose up -d
       docker compose ps -a
       docker compose logs --tail=60 guacamole
       docker compose logs --tail=40 guacd
        curl -I --max-time 10 http://127.0.0.1:8080/guacamole/

The expected state is guacamole Up, guacd Up/healthy, and guac-postgres Up/healthy. A 200 or 302 response from the HTTP
check means the web endpoint is responding; a container start message alone is not enough because Tomcat may still be
deploying the web application.

8. First login and configuring the RDP connection

8.1 Access the portal over SSH

From Windows PowerShell, use a local port forward. Keep this terminal open while using the browser:

       ssh -N -L 8080:127.0.0.1:8080 root@142.93.197.124

Browse to `http://127.0.0.1:8080/guacamole/`. The host-side Docker mapping is intentionally `127.0.0.1:8080:8080`, not
`0.0.0.0:8080:8080`. If PowerShell reports “channel open failed: connect failed: Connection refused”, check that the
Guacamole container is running and port 8080 is listening on the server loopback.

8.2 Secure the Guacamole administrator

The default `guacadmin` / `guacadmin` credentials were used during initial login. Confirm the administrator password was
changed; if it was not, change it immediately. Do not store the password in this runbook.

Why certificate handling matters: the original log recorded `Certificate validation failed` and an SSL/TLS failure because
XRDP presented a self-signed certificate. The TLS handshake subsequently succeeded, and XRDP logged successful
authentication for xmldesktop. For production, prefer a properly trusted RDP certificate; if using the “ignore certificate”
option, keep the RDP target private to the host bridge and understand that server identity is not validated.

9. Folder access and administrator permissions

9.1 Verify the folder before changing ACLs

The folder was referred to as `/opt/xmlfiles` during troubleshooting, but the transcript does not contain a final `ls -ld`
result. Verify the real path before applying permissions:

         ls -ld /opt/xmlfiles
      namei -l /opt/xmlfiles
        getfacl /opt/xmlfiles


9.2 Grant xmldesktop file access without changing ownership

Root already has administrative control; assigning ACLs to root is usually unnecessary. To grant xmldesktop read/write
access to files, traversal and modification in directories, and access to future items, run the following only after confirming
the path and business ownership. This keeps existing owners intact and uses capital `X` to add execute only to directories
and to files that are already executable.

       apt install -y acl
        setfacl -R -m u:xmldesktop:rwX /opt/xmlfiles
        find /opt/xmlfiles -type d -exec setfacl -m d:u:xmldesktop:rwx {} +
        getfacl /opt/xmlfiles

If policy specifically requires an explicit ACL entry for root too, use `setfacl -R -m u:root:rwx,u:xmldesktop:rwX /opt/xmlfiles`
and add default root ACLs on directories. Root normally retains access regardless. Do not use recursive `chown` unless you
intend to change ownership of the folder and all descendants.

9.3 Sudo is different from file access

The user `xmldesktop` was added to the `sudo` group. This grants the user administrative command access after a new
login session, but it is separate from ACLs that control access to `/opt/xmlfiles`. The verified group output included
`27(sudo)`. Test with `sudo whoami`, which should print `root`.

12. Backup, restore and rollback procedures

12.1 Before any upgrade or downgrade

      cd /opt/guacamole
      umask 077
      mkdir -p /root/guac-backups
      STAMP=$(date +%F_%H%M%S)
       docker exec guac-postgres pg_dump -U guac_user -d guac_db > "/root/guac-backups/guac_db_${STAMP}.sql"
        test -s "/root/guac-backups/guac_db_${STAMP}.sql" && echo "DB backup created"
      cp -a compose.yaml "/root/guac-backups/compose_${STAMP}.yaml"
      cp -a .env "/root/guac-backups/env_${STAMP}"
      chmod 600 "/root/guac-backups/"*

The backup file contains authentication and connection metadata; the `.env` backup contains a secret. Keep them root-
readable only and move a copy to encrypted off-server storage. Do not include a database dump or .env file in a public
repository.

12.2 Application-version rollback

•   Step 1: Take the database and configuration backups above before changing tags.
•   Step 2: Back up the current Compose file separately and edit the image tags for both `guacamole` and `guacd`
    together. Do not mix versions unless explicitly supported.
•   Step 3: Adjust PostgreSQL environment variable names to the exact version you are deploying; see Appendix C.
•   Step 4: Pull and recreate only the relevant containers, then inspect logs and test an RDP session. Keep the PostgreSQL
    volume and database intact unless there is a documented migration plan.

       docker compose config -q
       docker compose pull
       docker compose up -d --force-recreate guacd guacamole
       docker compose ps -a
       docker compose logs --tail=80 guacamole
       docker compose logs --tail=80 guacd
        curl -I --max-time 10 http://127.0.0.1:8080/guacamole/

 Version rollback caveat: A database schema may be changed by a later application version. A container image rollback
  is not a guaranteed database rollback. Read the exact release/upgrade notes and restore a compatible database backup
   if needed. Do not restore a dump over the live DB without stopping writes and verifying the target database.


12.3 Restore a PostgreSQL backup (destructive to current DB contents)

Only use this during a planned recovery window, after confirming the correct backup and target database. The following
pattern shows how to restore into a deliberately recreated database; it is not a one-click command for the live production
DB.

     # 1. Stop the web app so it cannot write while restoring
       docker compose stop guacamole

     # 2. Create a safety dump of the current DB before restoration
       docker exec guac-postgres pg_dump -U guac_user -d guac_db > /root/guac-backups/pre_restore_$(date +%F_%H%M%S).sql

     # 3. Select an approved recovery plan: restore into a new temporary database first,
     #  validate it, then perform the planned cutover. Do not pipe an old dump into
     #  the live database without clearing/isolating the current schema as planned.

     # 4. Start application and validate after recovery
       docker compose up -d guacamole
       docker compose ps -a

The commands intentionally stop short of dropping/recreating the live database because the existing schema and backup’s
exact origin must be established before a destructive restore. For true repeatable disaster recovery, rehearse restoring to a
separate temporary PostgreSQL database and document the tested cutover procedure.
