Deploying a Private Browser-Based Linux Desktop

A practical implementation of a remotely accessible Ubuntu XFCE desktop using Apache Guacamole, XRDP, PostgreSQL and Docker Compose — with the browser portal kept private behind an SSH tunnel.

Project overview

The objective was to provide a lightweight Linux desktop that could be accessed through a web browser, without exposing the remote desktop protocol or the Guacamole application directly to the public internet. The implementation separates the browser-facing gateway, RDP proxy, desktop service and authentication database.

Design principle: SSH is the external access path. Guacamole is bound to the Ubuntu host's loopback interface, while XRDP, guacd and PostgreSQL remain on private host or Docker networking paths.

What was implemented

  • Ubuntu host prepared with XFCE and XRDP.
  • Dedicated Docker bridge network for the Guacamole stack.
  • Guacamole, guacd and PostgreSQL deployed with Docker Compose.
  • Guacamole web endpoint published only on 127.0.0.1:8080.
  • SSH local port forwarding from the Windows workstation.
  • RDP connection configured to reach XRDP through the Docker bridge gateway.

What the runbook leaves for verification

  • Confirmation that the default Guacamole administrator password was rotated.
  • Final path and ACL validation for the shared files directory.
  • Longer-duration desktop and reconnect stability testing.
  • Encrypted off-server backup and restore rehearsal.
  • Any future public HTTPS access design.

Architecture and traffic flow

The topology below follows the deployed design documented in the operations runbook. The only intended public-facing management path is SSH; the browser accesses the Guacamole service through a local forwarded port.

The Docker bridge subnet and host gateway were configured specifically so guacd could reach XRDP without publishing RDP on a public interface. The exact public server address is intentionally omitted from this portfolio page.

Implementation

Prepare the Ubuntu hostUpdated Ubuntu Server 24.04.5 LTS and installed XFCE, the XFCE session components, XRDP and supporting packages.
Configure the desktop sessionCreated a dedicated Linux desktop account and configured its .xsession to launch xfce4-session.
Create the Docker networkUsed a dedicated bridge network named desktop-net, with a private subnet and gateway for container-to-host communication.
Bind XRDP privatelyConfigured XRDP to listen on the Docker bridge gateway at TCP 8933 rather than a public interface or the default public RDP port.
Deploy the Guacamole stackUsed Docker Compose for Guacamole, guacd and PostgreSQL, with persistent database storage and private container networking.
Connect securely from WindowsCreated an SSH local port forward and opened the Guacamole portal in a local browser session.

Example: browser access through SSH forwarding

The following is the documented access pattern. The server address is represented by a placeholder rather than publishing the host's public IP.

ssh -N -L 8080:127.0.0.1:8080 <ssh-user>@<server-public-ip>

# Open in the local browser:
http://127.0.0.1:8080/guacamole/

Example: validating the services

cd /opt/guacamole
docker compose config -q
docker compose ps -a
docker compose logs --tail=60 guacamole
docker compose logs --tail=40 guacd
curl -I --max-time 10 http://127.0.0.1:8080/guacamole/

# Check the private XRDP listener
ss -lntp | grep ':8933'

Challenges and troubleshooting

Issue encounteredInvestigation and resolution
Guacamole could not reach XRDPXRDP binding and host firewall rules were aligned with the dedicated Docker bridge. The final rule restricted TCP 8933 to traffic from the Docker subnet on the bridge interface.
XRDP certificate validation failedThe default XRDP certificate was self-signed. The connection's certificate handling was adjusted for the private test path; a trusted certificate remains a hardening consideration.
RDP session disconnected after loginThe observed Guacamole 1.6.0 / guacd 1.6.0 session failure matched a reported RDP display-layer assertion issue. Both Guacamole components were rolled back together to 1.5.5, after which desktop access succeeded.
Guacamole container restarted after downgradeThe Compose configuration used the wrong PostgreSQL username environment variable for version 1.5.5. It was changed from POSTGRESQL_USERNAME to POSTGRESQL_USER.
SSH tunnel reported connection refusedThe SSH connection itself was available, but the forwarded destination was not accepting connections while the Guacamole container was down. Container health and the host listener were checked first.
Desktop terminal did not recognize sudo membershipThe desktop account's group membership was refreshed by logging out and starting a new session after adding it to the sudo group.
Version lesson: Guacamole's Docker environment variable names differ between releases. The configuration must match the exact application version. The runbook records 1.5.5 as the final observed version after rollback; it does not claim that this is the latest or permanently fixed release.

Security and operational considerations

Controls applied in the documented design

  • Guacamole web port bound to host loopback only.
  • XRDP restricted to the Docker bridge gateway and bridge-originating traffic.
  • guacd and PostgreSQL kept on the internal Docker network.
  • SSH key-based administration used for host access.
  • Database credentials stored in a protected environment file, not in source control.

Hardening still to complete or re-verify

  • Rotate and verify the Guacamole administrator password.
  • Review SSH root-login policy and restrict SSH source IPs where practical.
  • Verify the target shared-folder path and ACLs before granting access.
  • Test session stability and reconnection over a longer period.
  • Store encrypted off-server backups and rehearse a restore.
  • Use a separately designed HTTPS reverse-proxy deployment if direct browser access is required.
The portal was not configured for direct public HTTP/HTTPS access in the documented deployment. Do not expose TCP 8080, 8933, 4822 or 5432 directly to the internet as a shortcut.

Outcome

The deployment achieved its core objective: a browser-accessible XFCE desktop on the DigitalOcean Ubuntu droplet, reached through an SSH local tunnel. The runbook records Guacamole and guacd 1.5.5 running, PostgreSQL healthy, the web portal bound to host loopback, and a successful desktop connection after troubleshooting.

The work also produced a repeatable operational record covering host preparation, desktop session configuration, Docker networking, XRDP binding, firewall rules, database initialization, validation, troubleshooting, backup and rollback. Remaining security and resilience tasks are clearly identified rather than presented as completed.
